## Context

The LocalCloud console (Solid.js + Armeria Java gateway) currently has 6 pages: Dashboard, Services, Logs, Data Browser, Usage, and Settings. The Logs page shows a flat table of requests with method/path/status/latency, polled every 3 seconds. The Data Browser supports browsing and basic CRUD. There is no request detail inspection, no cross-service tracing, no interactive query editors, no chaos testing, and no event replay.

The Java gateway already has `RequestLogger` (captures method, path, status, duration, service), `EventBus` (cross-service event propagation), and `IamMiddleware`. These provide the server-side foundation for most proposed features.

## Goals / Non-Goals

**Goals:**
- Transform the console from a monitoring dashboard into a full developer debugging environment
- Provide capabilities impossible in production: zero-sampling, full payload capture, fault injection, event replay
- Reduce time-to-debug from "deploy → check cloud logs → guess" to "see it happen in real-time"
- Help developers learn how GCP services actually work by making internals visible

**Non-Goals:**
- Replacing GCP Console for production use
- Supporting multi-user/team features
- Production-grade security (this is a local dev tool)
- Mobile-responsive design

## Decisions

### D1: Request body capture in RequestLogger

Extend `RequestLogger.RequestLogEntry` to include `requestBody` and `responseBody` fields (byte arrays). Capture is enabled by default with a 1MB max per body. Add a config flag `localcloud.log.capture-bodies=true|false` for opt-out.

Bodies are stored in a bounded ring buffer (last 1000 requests) to prevent memory bloat. Older entries drop their bodies but keep metadata.

### D2: Correlation IDs via X-Trace-Id header

Generate a UUID `traceId` for each incoming request in the API gateway. Propagate it:
- As `X-Trace-Id` header on proxied requests to external emulators
- As an attribute on EventBus events
- As a field in Cloud Logging entries

Store the traceId in `RequestLogEntry`. The frontend groups entries by traceId to build trace views.

### D3: WebSocket for real-time log streaming

Add a WebSocket endpoint at `/_localcloud/ws/logs` that pushes new request log entries as they arrive. The Armeria gateway implements this directly. This replaces 3-second polling.

Fall back to polling if WebSocket is unavailable (e.g., behind certain proxies).

### D4: Query console architecture

The BigQuery and Spanner query consoles reuse existing `BrowseService` patterns:
- BigQuery: `POST /_localcloud/query/bigquery` with `{dataset, sql}` body → proxies to BigQuery `jobs.query` API
- Spanner: `POST /_localcloud/query/spanner` with `{instance, database, sql}` body → creates session, executeSql, returns results, deletes session
- Memorystore: `POST /_localcloud/query/memorystore` with `{command}` body → executes via Redis RESP protocol

Results return a uniform `{columns: [...], rows: [...], error: null}` format.

### D5: Fault injection via gateway middleware

Add a `FaultInjector` middleware in the API gateway that intercepts requests before routing. Configuration stored in memory (not persisted):

```java
class FaultConfig {
    String service;
    int errorCode;        // 0 = no error injection
    int latencyMs;        // 0 = no latency injection
    int remainingCount;   // -1 = unlimited, N = next N requests
    double percentage;    // 0.0-1.0 for percentage-based
}
```

Admin API endpoints: `POST /_localcloud/faults` (set), `GET /_localcloud/faults` (list), `DELETE /_localcloud/faults` (clear).

### D6: Change diff via mutation tracking

Add a `MutationTracker` that records all write operations (with before/after state where possible) when recording is active. Admin API:
- `POST /_localcloud/diff/start` — start recording
- `POST /_localcloud/diff/stop` — stop recording, return accumulated changes
- `GET /_localcloud/diff/status` — check if recording is active

Changes are grouped by service and operation type (created/modified/deleted).

### D7: SDK snippets as static data in frontend

Code snippets are static content stored in the frontend (not generated by the backend). A JSON structure maps `{service, language}` to snippet templates with placeholders for port and env var. Languages: Python, Java, Go, Node.js.

### D8: Service topology from registry + EventBus

The topology graph is generated client-side from two data sources:
- `/_localcloud/services` — nodes (service names, ports, health)
- `/_localcloud/events/subscriptions` — edges (which services listen to which events)

Rendered using a simple force-directed or hierarchical layout (no heavy graph library — use SVG with manual positioning for the ~13 nodes).

## Risks / Trade-offs

**Request body capture increases memory usage** → Bounded ring buffer with configurable max entries (default 1000) and max body size (default 1MB). Worst case: 1000 * 2MB = 2GB. Mitigate by defaulting to metadata-only for bodies > 100KB.

**WebSocket adds complexity** → Fall back to SSE (simpler, one-directional) if WebSocket proves complex with Armeria. SSE is sufficient for log streaming.

**Fault injection could confuse developers** → Show a prominent banner in the console when any faults are active: "Fault injection active: GCS returning 503". Clear all faults on emulator restart.

**Change diff requires per-service state tracking** → Start simple: track by counting records before/after rather than detailed per-record diffs. Detailed diffs can come later.
